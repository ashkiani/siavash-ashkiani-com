Jailing an NVR: a local-first camera dashboard experiment

Security cameras are supposed to help protect a property. This lab explores a practical question: can an NVR keep doing its local recording job while being blocked from talking to the internet?

View the NVR dashboard repository →

The uncomfortable part

You buy a camera system to improve your security posture. Then you look at a packet capture from your own network and notice the device is reaching out to places you did not expect. That does not automatically mean something malicious is happening, but it does raise a fair privacy question: does this device need to talk to the outside world to do the job I bought it for?

A related story caught my attention. TechRadar covered a missing-person case where authorities recovered Nest doorbell footage even though the camera owner reportedly was not a Nest Aware subscriber. In that case, I am grateful the footage helped investigators. The privacy question is still worth asking, though: if camera data can exist outside the owner's direct control, even temporarily or unexpectedly, users should understand that tradeoff.

Reference: TechRadar: questions around recovered Nest doorbell footage.

That led me to this experiment: keep the NVR useful locally, but prevent it from calling home.

The idea: jail the NVR VLAN, add a trusted dashboard host

The pattern I am experimenting with is not just “block one device.” It is closer to a small network design: put the NVR and cameras on a restricted VLAN, block that VLAN from reaching the internet, and allow only a trusted host, such as a Raspberry Pi, mini PC, or VM, to talk to the NVR. Then selected internal VLANs, or a VPN-connected client, can access the dashboard instead of talking directly to the NVR.

Camera VLAN

Holds cameras, NVR, and the dashboard host. Outbound internet access is blocked.

NVR

Records locally and exposes compatible local endpoints for live view and playback.

Dashboard host

The Raspberry Pi/mini PC talks to the NVR and serves a local web dashboard.

Client access

Selected VLANs, or VPN users, can reach the dashboard. The NVR itself stays isolated.

Important compatibility note

This is not a universal NVR dashboard. The current code expects a system that exposes Lorex/Dahua-style local RTSP paths. For example, live view and playback paths similar to: 

/cam/realmonitor?channel=1&subtype=1
/cam/playback?channel=1&subtype=0&starttime=YYYY_MM_DD_HH_MM_SS&endtime=YYYY_MM_DD_HH_MM_SS

If an NVR does not expose compatible local HTTP/RTSP endpoints, this dashboard will probably not work without adapter code. Many camera systems use different URL formats, authentication behavior, codecs, or proprietary APIs.

What the dashboard currently does

The current implementation is intentionally small. It is not trying to replace a full vendor app. It focuses on the parts needed for a local security-camera workflow.

  • Shows selected camera streams in a browser on the local network.
  • Uses the NVR's local RTSP/HTTP interfaces from the server side, so credentials are not exposed in browser URLs.
  • Searches and exports playback windows from one or more cameras.
  • Can combine short playback segments into one exported clip when the NVR stores recordings in chunks.
  • Creates temporary source exports and optional browser-friendly previews.
  • Includes system checks, progress feedback, logs, and storage cleanup helpers for small deployments.

The tradeoff

This approach is not right for every camera system. If your setup depends on cloud-backed features such as object detection, motion alerts, human or vehicle detection, push notifications, app notifications, or two-way audio, isolating the NVR may disable some of those features.

That may make this a poor fit for a doorbell camera or any camera where cloud notifications and two-way talk are the main reason you bought it. But for a more traditional security-camera setup where the goal is simply to record locally and review footage when needed, the tradeoff can make sense.

Security notes

The dashboard is meant to be a local-only tool. The NVR credentials stay in a local configuration file on the dashboard host, and the dashboard should run as a dedicated low-privilege service account instead of a normal sudo-capable user. Exported clips should be treated as temporary artifacts and cleaned up automatically.

If remote access is needed, the safer pattern is to connect to your own network through a VPN and then open the dashboard. Do not expose the dashboard directly to the public internet.

This is still a lab project, not a commercial product. The goal is to make the privacy model explicit and give technically comfortable users a pattern they can adapt, not to claim that one setup is universally correct.
