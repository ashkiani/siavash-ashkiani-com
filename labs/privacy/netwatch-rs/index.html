netwatch-rs: watching the packets that enter and leave a computer

I wanted something between a temporary operating-system connection list and a full Wireshark capture: a readable live dashboard that remembers ended flows and lets me capture the activity that happened just before I noticed it.

View the repository → Download a release →

The gap I was trying to fill

Windows Resource Monitor, ss, netstat, and similar tools can show active connections, but the list may be difficult to interpret and short-lived entries disappear quickly. An IP address, port, and process name are useful pieces, but they do not always provide a clear picture when viewed separately.

Wireshark solves a different problem extremely well: it captures and decodes detailed packet data. The tradeoff is volume. A full capture can grow quickly and leave you searching through much more data than you needed to answer a simple question: what did this computer just talk to?

netwatch-rs is the middle ground I wanted. The current frontend is a terminal dashboard, while the capture and accounting core is kept separate so a future desktop widget can reuse it.

What the current release does

  • Captures visible IPv4, IPv6, TCP, UDP, ICMP, ICMPv6, ARP, and other packet types on selected interfaces.
  • Groups both directions of a conversation into one flow while keeping different local ports separate.
  • Shows rolling TX/RX totals for the last minute, hour, and 24 hours.
  • Keeps inactive flows visible for 24 hours and dims them instead of immediately removing them.
  • Adds best-effort process attribution for TCP and UDP sockets.
  • Learns hostnames passively from ordinary DNS replies without generating reverse-DNS traffic.
  • Keeps a bounded full-packet memory buffer for each observed flow.
  • Saves the selected flow's buffered history and matching live packets to a PCAPNG file.
  • Reports packets dropped by the application, capture driver, or interface.

Capturing what happened before I pressed Capture

A suspicious connection may be over by the time you decide to investigate it. Starting a normal capture at that point preserves what happens next, but the DNS reply, handshake, or first exchange may already be gone. 

visible packet
  → bidirectional flow
  → rolling counters + bounded in-memory packet history
  → press c
  → buffered history + matching live packets → PCAPNG

By default, each flow can retain up to 1 MiB and all flow buffers together can retain up to 256 MiB. The limits are configurable. Old packets or inactive flow buffers are evicted when necessary, and the packet history disappears when the program exits.

Minute-level traffic totals and flow metadata are stored in SQLite so the rolling history can survive a restart. Packet payloads are not stored in the database.

Design choices

One packet stream

A packet is captured once and used for accounting, retrospective buffering, and an active selected-flow capture.

Stable rows

New flows appear at the top, but existing rows do not shuffle as traffic arrives and the highlight stays with the selected flow.

Passive enrichment

DNS names come from traffic already observed. Missing process or hostname information remains unknown rather than delaying packet accounting.

Bounded memory

Per-flow and global byte limits prevent the retrospective packet history from growing without control.

Why Rust?

A long-running packet monitor needs to be efficient, and C would have been an obvious option. I had also wanted a real reason to learn Rust after hearing both the praise and criticism around it for several years. This project—with packet buffers, capture workers, bounded queues, binary output, and shared state—felt like the right test.

Rust's ownership rules made parts of the implementation more demanding, but they also forced memory ownership and error handling to be explicit. For this kind of systems tool, I liked that tradeoff.

Important limits and privacy notes

  • “Every packet” means every packet exposed by the operating system and capture driver on the selected interfaces. VPNs, virtual switches, containers, hardware offload, and driver policy can affect the view.
  • Normal monitoring is non-promiscuous. It observes host traffic and ordinary broadcast/multicast traffic, not unrelated conversations between other machines.
  • Process attribution is best-effort; a short-lived socket can close before the next operating-system snapshot.
  • DNS-over-HTTPS and DNS-over-TLS hide classic DNS replies, so some addresses will remain unnamed.
  • PCAPNG files may contain plaintext, credentials, or other private data. Review and sanitize captures before sharing them.

Project status

Version 0.1.0 is the first public release and currently supports Windows and Linux. Windows uses Npcap; Linux uses libpcap and requires packet-capture permission. The release archives include checksums but do not redistribute Npcap or libpcap.

This is an early-stage open-source project, not an intrusion-detection system. It does not decide whether a connection is malicious. It provides a readable history and a quick way to preserve relevant packets for deeper investigation.
